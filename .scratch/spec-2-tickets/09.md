## Parent

Part of #2 (Purchasing and goods receiving).

## What to build

Make receipt confirmation safe to retry. The confirm route takes a client-supplied idempotency key backed by a database unique constraint: repeating the same request with the same key returns the original receipt and makes no further change to stock or the order, while a deliberately new key records a second genuine delivery. This establishes the idempotency-key convention for the repository.

`Covers:` GR-04 (retries never double stock, replay returns original, new receipt still possible). AC-02.
`Demo:` staff_b01 confirms 8, then resends the same request → the original receipt is returned, stock stays 18, cumulative stays 8; a new key records a separate second receipt
`Seams:` oRPC controller spec; Postgres integration spec

## Acceptance criteria

- [ ] Resending a confirmation with the same idempotency key returns the original receipt and makes no further change to stock or cumulative received quantity (Postgres integration spec; fails today — no idempotency). [AC-02]
- [ ] From the starting data, receiving 8 then resending the same request leaves stock 18 and cumulative received 8 (Postgres integration spec; fails today). [AC-02]
- [ ] A confirmation with a new idempotency key records a separate, deliberate second receipt (oRPC controller spec; fails today). [GR-04]
