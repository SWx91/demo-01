LESSON 01⏱ 10–15 นาที

Monorepo, Turborepo และการเขียนโค้ดด้วย AI

ต้นฉบับ: 01-monorepo-and-turborepo.md
เป้าหมาย: เข้าใจว่า repo นี้จัดโครงสร้างอย่างไร ทำไมจัดแบบนั้น และทำไมโครงสร้างนี้ช่วยให้ AI agent ทำงานได้ดีขึ้น
  1. Monorepo คืออะไร ต่างจาก polyrepo อย่างไร
  2. Turborepo เพิ่มอะไรให้ monorepo และทำไมเลือกใช้
  3. โครงสร้างนี้ช่วยอะไรเมื่อให้ AI agent สร้างฟีเจอร์

Monorepo คืออะไร

  • Monorepo คือ Git repo เดียวที่มีหลายโปรเจกต์อยู่ด้วยกัน ในเวิร์กช็อปนี้ frontend, backend, API contract และ database schema อยู่ใน repo เดียว
  • Polyrepo คือแยก repo ละโปรเจกต์ โค้ดที่ใช้ร่วมกันต้อง publish เป็น package แล้วแต่ละ repo ค่อย install ทำให้เวอร์ชันไม่ตรงกันได้ง่าย
  • Monorepo ไม่ใช่ monolith: apps/web กับ apps/api ยังเป็นสองแอปที่ build และ deploy แยกกัน แค่อยู่ repo เดียวกัน
  • pnpm workspaces ทำให้ทุกโฟลเดอร์ใน apps/ และ packages/ เป็น package แยก และอ้างถึงกันด้วย "workspace:*" โดยไม่ต้อง publish
  • หัวใจคือ @erp/contracts ที่อธิบายทุก endpoint ไว้ที่เดียว ทั้ง API และ web ใช้ package นี้ จึงไม่มีทางเข้าใจ API ไม่ตรงกัน

Turborepo เพิ่มอะไรให้

  • Task graph: ใน turbo.json เขียน "dependsOn": ["^build"] แปลว่า "ก่อน build package นี้ ให้ build ทุก package ที่มันพึ่งพาก่อน" Turborepo จัดลำดับและรันงานที่ไม่เกี่ยวกันพร้อมกันให้เอง
  • Caching: คำนวณ hash จากไฟล์และ config ถ้าเคยเห็น hash นี้แล้วจะดึงผลลัพธ์เก่ามาใช้เลย build รอบสองที่ไม่มีอะไรเปลี่ยนเสร็จในไม่ถึงครึ่งวินาที
  • --filter: รันเฉพาะ package ที่สนใจ แต่ยัง build dependency ให้ก่อน ผลจึงถูกต้องและเร็ว
  • เลือก Turborepo เพราะเป็น ชั้นบางๆ: แต่ละ package ยังใช้ script ปกติ config ทั้งหมดราว 40 บรรทัด ถ้าถอดออก ทุก package ยัง build ได้เอง

ทำไมช่วย AI coding

  • ฟีเจอร์ทั้งก้อนอยู่ที่เดียว: schema, contract, API handler และ UI อยู่ใน checkout เดียว agent อ่านของจริงแทนการเดา
  • Vertical slices: ทำงานเป็นชิ้นบางที่ตัดผ่านทุกชั้น ปัญหาการต่อกันโผล่ตั้งแต่เฟสแรก ทุกเฟสรันและทดสอบได้ และแต่ละชิ้นเล็กพอให้ agent ถือ context ไหว
  • Compiler ช่วยรีวิว: type ทั้งหมดมาจาก contract ถ้า agent เปลี่ยนชื่อ field จุดที่ไม่ตรงจะกลายเป็น type error พร้อมไฟล์และบรรทัด agent แก้ error ที่มองเห็นได้เก่งกว่าหาบั๊กที่ไม่มีใครรายงาน
  • คำสั่งเดียวเช็คทุกอย่าง: pnpm check (lint + typecheck + test + build) เร็วเพราะ cache
  • คำสั่งแบบเป็นชั้น: AGENTS.md ที่ root เป็นกฎกลาง ส่วน apps/api และ apps/web มีกฎเฉพาะ stack ของตัวเอง
  • ระวัง: อย่าให้ agent อ่านทั้ง repo, อย่าแก้ไฟล์ที่ generate (dist/, Prisma client) และอย่าทำ diff ใหญ่เกินไป
pnpm check                                # lint + typecheck + test + build ทุก package
pnpm turbo run test --filter=@erp/api     # test เฉพาะ api (dependency ยัง build ก่อน)
pnpm turbo run build                      # รันสองครั้ง รอบสองแทบทั้งหมดมาจาก cache

สรุปบทที่ 1

  • Monorepo เก็บโปรเจกต์ที่เกี่ยวข้องไว้ repo เดียว ใช้โค้ดร่วมกันได้ทันที และหนึ่ง commit แก้ได้ทุกชั้น
  • Turborepo เพิ่ม task graph และ cache ให้ pnpm workspaces โดยแทบไม่ต้อง config
  • สำหรับ AI: เห็นฟีเจอร์ครบ, ทำเป็น vertical slice, ได้ type error เป็น feedback, มีคำสั่งเดียวตรวจงาน และมีคำสั่งแยกตาม stack
ถ้า agent รัน tsc ตรงๆ ใน apps/web หลังแก้ contract จะเกิดอะไร
มันจะ type-check กับ build เก่าของ contract และได้ผลที่สับสน ควรรันผ่าน Turborepo (pnpm check) เพราะ ^build จะ build dependency ใหม่ก่อน
ทำไม vertical slice เหมาะกับ monorepo
หนึ่ง slice แตะ schema, contract, API และ UI ใน monorepo คือ branch เดียว diff เดียว และ pnpm check ครั้งเดียว ส่วน polyrepo ต้องเปิด 3 PR และ publish contract ใหม่
LESSON 02⏱ 10–15 นาที

Context engineering: อะไรควรอยู่ใน AGENTS.md และอะไรควรเป็น skill

ต้นฉบับ: 02-context-engineering-agents-md-and-skills.md
เป้าหมาย: เข้าใจว่าทำไมไฟล์คำสั่งใน repo นี้ตั้งใจเขียนให้สั้น ทำไมสูตรยาวๆ ถูกย้ายไปเป็น skill และตัดสินใจเองได้ว่าเนื้อหาไหนควรอยู่ที่ไหน
  1. agent "มองเห็น" อะไรบ้างระหว่าง session และทำไมพื้นที่นั้นถึงเป็นงบประมาณ
  2. "dumb zone" คืออะไร ทำไมเริ่มก่อน context เต็มนาน
  3. เนื้อหาหนึ่งย่อหน้าควรอยู่ใน AGENTS.md, skill หรือลบทิ้ง

Context window คืองบประมาณ

  • ต้นทุนคงที่ (จ่ายทุก session): system prompt, นิยาม tool, ไฟล์คำสั่ง (AGENTS.md/CLAUDE.md) และชื่อกับคำอธิบายของทุก skill
  • ต้นทุนผันแปร (โตขึ้นเรื่อยๆ): ไฟล์ที่อ่าน, log ของ build และ test, บทสนทนา ซึ่งค้างอยู่จนกว่าจะ clear หรือ compact
  • ใน Claude Code ดูสัดส่วนได้ด้วย /context คำถามที่ดีคือ "ตอนนี้ context ส่วนไหนทำงานมีประโยชน์จริง"

Dumb zone

  • ความสามารถของโมเดลลดลงเมื่อ context ยาวขึ้น และลดตั้งแต่ก่อนเต็มนาน
  • Context rot: งานวิจัยของ Chroma (ก.ค. 2025) ทดสอบ 18 โมเดล ทุกตัวแย่ลงเมื่อ input ยาวขึ้น แม้งานจะง่ายเท่าเดิม
  • Lost in the middle: โมเดลจำต้นและท้าย prompt ได้ดี แต่จำตรงกลางได้แย่ ไฟล์คำสั่งที่โหลดก่อนจะถูกดันไปอยู่ตรงกลางเรื่อยๆ
  • กฎคร่าวๆ: พยายามใช้ context ราว 40–60% ถ้าเป็นโมเดล 200K ที่ 150K token ถือว่าอยู่ใน dumb zone แน่นอนแล้ว
  • อาการ: ลืมกฎที่เคยทำตาม, เสนอวิธีแก้ที่ลองไปแล้ว, เอารายละเอียดจากงานก่อนมาปน, ตอบผิดอย่างมั่นใจ วิธีแก้คือลด context ไม่ใช่เขียน prompt ให้ดีขึ้น
ทำไมเกี่ยวกับไฟล์คำสั่ง: AGENTS.md ยาว 300 บรรทัดเสียสามต่อ คือกินงบตั้งแต่ต้น, ถูกดันไปอยู่ตรงกลางที่โมเดลอ่านแย่ที่สุด และกฎที่ไม่เกี่ยวกับงานตอนนั้นกลายเป็นตัวหลอก กฎยิ่งยาว agent ยิ่งทำตามได้น้อยลง

กฎ (always on) กับ สูตร (on demand)

  • กฎ สั้น ใช้กับเกือบทุกงาน และพลาดแน่ถ้าไม่รู้ เช่น "relative import ต้องลงท้าย .js", "ห้ามเขียน API type เอง ให้ derive จาก contract" ใส่ใน AGENTS.md
  • สูตร ยาว ใช้กับงานประเภทเดียว เช่น ขั้นตอนเพิ่มฟีเจอร์ 6 ขั้น, template ของ test ใส่เป็น skill
  • Progressive disclosure: ตอนเริ่ม session agent โหลดแค่ชื่อและคำอธิบาย skill บรรทัดเดียว เมื่องานตรงกับคำอธิบายจึงอ่านเนื้อหาเต็ม คำอธิบายจึงต้องบอกทั้ง "มีอะไร" และ "ใช้เมื่อไหร่"
  • Skill เป็น format เปิด ใช้ได้ทั้ง Claude Code, Codex, Cursor และ Kiro เก็บจริงที่ .agents/skills/ แล้ว symlink ไปโฟลเดอร์ของแต่ละเครื่องมือ

ผลที่เกิดใน repo นี้

ไฟล์ AGENTS.md สามไฟล์ลดจาก 52/24/26 บรรทัด (ราว 1,800 token) เหลือ 34/10/9 บรรทัด (ราว 1,000 token) และได้ skill สามตัว (add-feature, write-tests, repo-commands) ราว 2,900 token ที่โหลดเมื่อจำเป็น ต้นทุนคงที่ลดลงครึ่งหนึ่ง แต่ความรู้ที่ agent เข้าถึงได้ เพิ่มขึ้น เพราะ skill ใส่ template เต็มได้ ส่วนที่ลบทิ้ง เช่น การตั้งค่า Prettier (มี .prettierrc อยู่แล้ว) และกฎที่ซ้ำกันในหลายไฟล์

วิธีอื่นที่ช่วยได้

  • เริ่มใหม่ระหว่างงาน: /clear ทิ้งบทสนทนาแต่เก็บต้นทุนคงที่ไว้
  • Compact อย่างตั้งใจ: ให้ agent เขียนสิ่งที่เรียนรู้ลงไฟล์ แล้ว clear และทำต่อจากไฟล์นั้น
  • ส่งงานสำรวจให้ subagent: อ่าน 20 ไฟล์แล้วส่งกลับแค่ 3 ประโยค (บทที่ 6)
  • ใช้การตรวจแบบ deterministic: type error ไม่กี่บรรทัดดีกว่าสั่งให้ "ไล่หาจุดที่ไม่ตรงกัน"
  • นับจำนวน tool: MCP server แต่ละตัวโหลดนิยาม tool ทั้งหมดตอนเริ่ม 5 server อาจกินมากกว่าไฟล์คำสั่งทั้ง repo

สรุปบทที่ 2

  • Context window คืองบประมาณ มีทั้งต้นทุนคงที่และต้นทุนที่โตขึ้นตลอด session
  • โมเดลแย่ลงก่อน context เต็มนาน smart zone อยู่ราว 40% แรก ที่ 150K บนโมเดล 200K คือ dumb zone
  • กฎสั้นใส่ AGENTS.md, สูตรยาวใส่ skill, อะไรที่ agent หาเองได้ให้ลบ
"ใช้ single quote, trailing comma, กว้าง 100" ควรอยู่ที่ไหน
ลบทิ้ง เพราะ .prettierrc คือแหล่งความจริงอยู่แล้ว และ pnpm format จัดให้เอง เขียนซ้ำในไฟล์คำสั่งเป็นต้นทุนเปล่า
ทำไมคำอธิบาย skill "Testing notes" ถึงไม่ดี
คลุมเครือ agent ตัดสินจากคำอธิบายบรรทัดเดียว จึงอาจไม่เคยโหลดเลยหรือโหลดทุกงาน ควรเขียนให้บอกว่ามีอะไรและใช้เมื่อไหร่ เช่น "วิธีเขียนและรัน *.spec.ts และ *.test.tsx ใช้เมื่อเพิ่มหรือแก้ test"
LESSON 03⏱ 15–20 นาที

เริ่มต้นให้สะอาด: รีเซ็ต agent, ล็อกค่าโปรเจกต์, ปิด memory

ต้นฉบับ: 03-clean-agent-setup.md
เป้าหมาย: ให้ทุกคนในห้องใช้ agent แบบเดียวกันบน repo เดียวกัน โดยไม่มีอะไรถูกโหลดที่มองไม่เห็นใน git
  1. config ของ agent มาจากไหน และทำไมการตั้งค่าส่วนตัวถึงเปลี่ยนพฤติกรรมใน repo นี้
  2. รีเซ็ต agent ให้เหมือนติดตั้งใหม่โดยไม่เสียอะไรและไม่ต้อง sign out ได้อย่างไร
  3. ทำไมต้องปิด memory อัตโนมัติ และใช้อะไรแทน

Config สามชั้น

  • Global config (ใน home directory): settings, ไฟล์คำสั่งส่วนตัว, skill, MCP server, plugin, hook ของแต่ละคน โหลดในทุกโปรเจกต์
  • Project config (ใน repo): AGENTS.md, skill ใน .agents/skills/ และ project settings ถูก commit จึงเหมือนกันทุกคน
  • Memory: โน้ตที่ agent เขียนไว้เองจาก session ก่อนแล้วโหลดกลับมา
  • มีแค่ชั้นกลางที่เหมือนกันทุกเครื่อง ตัวอย่างปัญหา: คนหนึ่งมี GitHub MCP 40 tool, อีกคนมีคำสั่งส่วนตัวว่า "ใช้ npm เสมอ" (repo นี้ใช้ pnpm), อีกคนมี memory จากโปรเจกต์อื่น ผลคือพิมพ์ prompt เดียวกันแต่ได้ผลต่างกัน

ขั้นที่ 1: รีเซ็ต global config

Hooks: ด่านกั้นระหว่าง agent กับ shell

ต้นฉบับ: 05-hooks-guard-the-shell.md
เป้าหมาย: ลงทะเบียน hook หนึ่งตัวที่โปรเจกต์เลือกและ commit ไว้ เพื่อกันไม่ให้ agent รันคำสั่งทำลายล้าง 4 แบบ ไม่ว่าจะใช้เครื่องมือไหน
  1. hook คืออะไร และทำอะไรได้ที่กฎใน AGENTS.md ทำไม่ได้
  2. ทำไมบท 3 ปิด hook และทำไมบทนี้เปิดหนึ่งตัว
  3. CI ครอบคลุมอะไรแล้ว และเหลืออะไรให้ hook ทำ

Hook คืออะไร

  • hook คือคำสั่ง shell ที่ harness รันในจังหวะที่กำหนด ส่ง JSON เข้า stdin แล้วอ่าน exit code
  • มีหลายจังหวะ (SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, Stop, SessionEnd) แต่ PreToolUse เป็นจังหวะเดียวที่ปฏิเสธการกระทำได้
  • hook ไม่ใช่ โมเดลหรือ prompt แต่เป็นโปรแกรมที่รันทุกครั้ง agent ใน dumb zone อาจลืมกฎ "ห้าม reset database" แต่ hook ไม่ลืม
Exit codeสิ่งที่ harness ทำ
0รันคำสั่งตามแผน
2ไม่รัน และส่งข้อความ stderr กลับไปเป็นเหตุผลให้ agent
อื่นๆรันต่อและแสดง stderr เป็นคำเตือน (hook พัง = เปิดผ่าน ไม่ใช่ปิดกั้น)

CI ทำอะไรไม่ได้

CI ตรวจ diff ที่ push ขึ้นไปหลังจากนั้นหลายนาที ไม่สามารถหยุดอะไรได้ ส่วนคำสั่งอย่าง pnpm db:reset (ลบทุกตาราง), docker compose down -v (ลบ volume ของ Postgres), git push --force (เขียนประวัติใหม่), rm -rf (ลบไฟล์ที่อาจยังไม่ commit) ไม่ทิ้งร่องรอยใน diff และ agent ที่ติดขัดมักหยิบมาใช้

ทำไมบท 3 ปิดแต่บทนี้เปิด

เรื่องของ ที่มา (provenance) hook ใน home directory รันในทุก repo โดยไม่มีใครเห็น ส่วน hook ในบทนี้อยู่ใน repo ทุกคนที่ clone ได้ตัวเดียวกัน อ่านได้ใน 30 วินาที และดูใน git log ได้ว่าใครเพิ่ม

Database resetprisma migrate reset, pnpm db:resetลบทุกตารางแล้วรัน migration ใหม่
ลบ Docker volumedocker compose down -v, docker volume rm/pruneลบข้อมูล Postgres

ลงทะเบียนและทดสอบ

  • อัปเดต Kiro ก่อน (kiro-cli update) แล้วใช้ prompt ให้ agent อ่านเอกสารของตัวเองและเขียน registration (ห้ามเดา key)
  • Kiro: เพิ่ม hooks ใน .kiro/agents/erp.json ด้วย trigger PreToolUse และ matcher ^(execute_bash|execute_pwsh)$
  • Claude Code: ลบ disableAllHooks แล้วเพิ่ม hooks.PreToolUse ที่ matcher Bash ใน .claude/settings.json
  • Codex: .codex/hooks.json และตั้ง hooks = true ใน config.toml
  • ทดสอบ: สั่ง "Reset the development database with pnpm db:reset" ต้องถูกบล็อก, สั่ง "pnpm db:migrate" ต้องรันได้ แล้ว commit บน main

สรุปบทที่ 5

  • hook คือโปรแกรมที่ harness รันในจังหวะที่กำหนด ก่อน tool call ถ้า exit 2 จะบล็อกและส่งเหตุผลกลับ และไม่เคยลืม
  • CI ตรวจผลลัพธ์หลัง push ส่วน hook ตรวจการกระทำก่อนรัน
  • guard มี 4 กฎในสคริปต์สั้นๆ ใช้ร่วมกันทั้ง 3 เครื่องมือ ไม่ใช่ sandbox และไม่ตัดสิน diff

Subagent คืออะไร

  • เป็น session ที่สองที่ agent หลักสร้างขึ้น มี context window, คำสั่ง และ tool ของตัวเอง agent หลักเขียน brief ให้แล้วรอ รายงาน กลับมา สิ่งเดียวที่เข้า window หลักคือรายงาน
  • แชร์: ไฟล์, git checkout, ไฟล์คำสั่ง, skill และสิทธิ์ ไม่แชร์: บทสนทนา เหมือนส่งคำถามให้เพื่อนร่วมงานห้องข้างๆ
  • Brief คือทุกอย่าง: subagent รู้แค่สิ่งที่เขียนให้ ใช้ "context pointer" เช่น เลข ticket, spec, path ไฟล์
  • รายงานคือสิ่งเดียวที่กลับมา: ถ้าไม่เขียนในรายงานก็หายไปเมื่อ window ปิด
  • ไม่ฟรี: แต่ละตัวจ่ายต้นทุนคงที่ใหม่ คุ้มเมื่องานสร้าง token เยอะที่ window หลักไม่ต้องเก็บ หรือเมื่อสองงานจะปนกันถ้าทำใน window เดียว

Subagent เป็นผู้ลงมือ (อ่านไว้ ยังไม่ต้องรัน)

  • implement-spec: orchestrator ส่ง ticket แต่ละตัวใน frontier ให้ implementer subagent คนละ git worktree ทำงานเบื้องหลัง แล้ว merger subagent รวมเข้า integration branch ตอนนี้ทำได้เต็มรูปแบบแค่ใน Claude Code

LESSON 07⏱ 45–60 นาที

จาก ticket สู่โค้ด: หนึ่งรอบของ implement loop

ต้นฉบับ: 07-from-tickets-to-code.md
เป้าหมาย: หยิบ ticket แรกที่ไม่ถูกบล็อกจากบทที่ 4 ให้ agent สร้างใน window ใหม่ และจบด้วย pull request ที่คุณและ CI พิสูจน์แล้ว พร้อมให้คนอื่นรีวิวและ merge
  1. ทำไม agent ได้ ticket เดียว ใน window ใหม่ และไม่มีอะไรอื่น
  2. implement skill ทำอะไร และ loop รอบๆ มันต้องทำอะไร
  3. หน้าที่ของคุณในแต่ละรอบคืออะไร และทำไม loop หยุดก่อน merge

Skill implement มีแค่ 7 บรรทัด

  • ดึง ticket และบอกชื่อก่อนเริ่ม → เรียก tdd ที่ seams ที่ตกลงกันไว้ → typecheck และรัน test บ่อยๆ, รันทั้งชุดตอนท้าย → เรียก code-review → commit
  • สิ่งที่ ไม่ทำ: ไม่สร้าง branch, ไม่เปิด PR, ไม่ปิด ticket, ไม่ติ๊ก checkbox, ไม่หา ticket ถัดไป สิ่งเหล่านี้คือ "loop" และเป็นหน้าที่ของคุณ
  • implement-ticket (skill ของ repo นี้) เพิ่มกฎ 6 ข้อ: อยู่ branch เดิมและใส่ #N ใน commit, แสดง seams แล้วรอคำยืนยัน, pnpm check และ pnpm format ต้องผ่าน, review หลัง commit โดยเทียบกับ main, push และเปิด PR ที่มี Closes #N, ห้ามปิดหรือติ๊ก ticket
ทำไม review หลัง commit: code-review diff ประวัติที่ commit แล้วเทียบกับจุดคงที่ แต่ implement เรียกมันก่อน commit ทำให้มักเห็น diff ว่างและไม่รายงานอะไร การ commit ก่อนแล้ว review เทียบกับ main คือทางแก้

ก่อนเริ่ม

gh repo set-default                   # เลือก fork ของตัวเอง ไม่ใช่ repo ต้นฉบับ
# เปิด Actions บน fork ที่ github.com (fork ปิด workflow ไว้)
npx skills@latest add mattpocock/skills --skill pr   # แล้ว commit บน main ก่อนแตก branch
pnpm dev:local                        # Postgres + migrate + seed + ทั้งสองแอป

  1. บอกชื่อ ticket ถ้าไม่ใช่ ticket ของคุณให้หยุด
  2. สำรวจและเสนอ seams ตอบ yes ถ้าตรงกับบรรทัด Seams: ถ้าเสนอ seam ที่ ticket ไม่ได้ระบุให้ถามเหตุผล
  3. Red แล้ว green ทีละ slice ถ้าเห็นเขียน test ทั้งหมดก่อนแล้วค่อยเขียนโค้ด นั่นคือ horizontal slicing ให้ทักท้วง
  4. Commit แล้ว review subagent สองตัวรายงานใต้ ## Standards และ ## Spec แก้แล้ว commit อีกครั้ง
  5. Push และเปิด PR จบด้วย URL

ใช้เวลา 20–40 นาที และเกิน 100K token ห้าม /compact กลางทาง ถ้า window เต็มก่อนได้ PR ให้ commit ส่วนที่ผ่าน, /clear, แล้วรันใหม่พร้อมบอกว่า "branch มีงานบางส่วนแล้ว อ่าน commit ก่อน"

ตาของคุณ: demo, diff, boxes, CI

  • ทำตามบรรทัด Demo: เช่น login เป็นผู้ใช้ทดสอบแต่ละคนแล้วดูว่า /api/auth/me คืน role และ store ถูก ถ้าเดโมไม่ผ่าน ticket ยังไม่เสร็จ ไม่ว่า test จะว่าอย่างไร
  • อ่าน diff เทียบกับเกณฑ์: หา test หรือโค้ดที่ทำให้เกณฑ์แต่ละข้อเป็นจริง เกณฑ์ที่หาไม่เจอคือเกณฑ์ที่ agent ตัดสินเองว่าผ่านแล้ว
  • ติ๊ก checkbox บน GitHub เอง เป็นหลักฐานว่าคนได้ตรวจแล้ว
  • รอ CI เขียว ถ้าแดง แปะ output ลงใน session เดิมให้ agent แก้ เขียวแล้วจึง /clear

บทนี้ ไม่ merge PR ต้องให้คนที่ไม่ใช่ผู้เขียนอ่านก่อน (บทที่ 8 เพิ่ม AI reviewer มาช่วย) เหตุผลคือเมื่อ merge แล้ว ticket ที่ถูกบล็อกทั้งหมดจะเปิดให้ทำ ticket ที่ยังไม่ได้พิสูจน์จะเปิดประตูให้ทุกงานที่ตามมา

เมื่อ ticket ผิด

agent ห้ามตีความ ticket ใหม่เอง กฎคือ หยุด, แก้ issue, /clear, เริ่มใหม่ ถ้า agent ถามสิ่งที่ ticket ควรตอบ ให้ตอบบน ticket ไม่ใช่ในแชท เพราะ session ถัดไปและ reviewer จะไม่เห็นคำตอบในแชท

สรุปบทที่ 7

  • หนึ่ง ticket หนึ่ง window ใหม่ บทสนทนาทิ้งได้ spec, ticket, dependency, branch และ PR คือ state
  • implement แค่ fetch, TDD, check, review, commit ส่วน loop รอบนอกเป็นของคุณ กฎของ repo อยู่ใน implement-ticket
  • หน้าที่คุณคือ demo, diff, ติ๊กเกณฑ์, CI เมื่อ ticket ผิดให้แก้ที่ ticket และ loop หยุดที่ PR
ทำไมสร้าง branch เองแทนให้ agent สร้าง
skill commit ลง branch ที่มันอยู่และไม่เคยสร้าง branch คำสั่ง shell บรรทัดเดียวเชื่อถือได้มากกว่าการหวังให้ agent จำได้
ทำไม agent ห้ามติ๊ก checkbox หรือปิด ticket เอง
การให้ agent พิสูจน์งานของตัวเองคือสิ่งที่ loop ออกแบบมาไม่ให้เชื่อ การปิดเป็นหน้าที่ของการ merge การติ๊กเป็นหน้าที่ของคุณ

AI รีวิวทุก Pull Request: Kiro ใน GitHub Actions

ต้นฉบับ: 08-ai-reviews-the-pull-request.md
เป้าหมาย: ติดตั้ง reviewer agent แบบอ่านอย่างเดียวบน fork ที่อ่าน ticket, diff และ PR body ของทุก PR เขียนรีวิวหนึ่งฉบับให้ job โพสต์เป็น comment และไม่เคย approve, merge หรือปิดอะไร แล้วให้คน merge PR จากบทที่ 7 โดยใช้รีวิวนั้นเป็นบท
  1. reviewer ที่ไม่เห็นตอนเขียนโค้ดหาอะไรเจอที่ผู้เขียนหาไม่เจอ และยังทำอะไรไม่ได้
  2. ทำให้ agent อ่านอย่างเดียวได้อย่างไร และทำไม "ห้าม approve ห้าม merge" ถูกบังคับสามชั้น
  3. ทำไม AI review เป็นคำแนะนำให้คน ไม่ใช่สถานะบน GitHub

มันคืออะไร และไม่ใช่อะไร

  • คล้าย CodeRabbit หรือ Copilot code review แต่รีวิว เทียบกับ acceptance criteria ของ ticket และ AGENTS.md brief เป็นไฟล์ใน repo ที่แก้ได้ และใช้ guard hook เดียวกับบทที่ 5
  • reviewer หยิบ branch ขึ้นมาแบบเย็นชา (cold) ไม่ได้ brief จากผู้เขียน แก้ปัญหาแรกของบทที่ 7 ได้ แต่ ไม่มี database และแอปใน job บรรทัด Demo จึงยังเป็นหน้าที่คน
  • บรรทัดสุดท้ายของรีวิวคือ คำแนะนำ ไม่ใช่ approval GitHub แสดงเป็น comment ไม่ใช่เครื่องหมายถูกสีเขียว

kiro-cli chat --v3 --no-interactive --agent reviewer "Review pull request #18."
gh pr review 18 --comment --body-file .ai-review/review.md   # โพสต์เองครั้งเดียว

# หลัง commit .github/workflows/ai-review.yml บน main
gh workflow run ai-review.yml -f pr=18
gh run watch
  • workflow แยกจาก ci.yml: CI คือ test ที่บล็อก merge ได้ ส่วนรีวิวคือความเห็นที่ไม่ควรทำให้ CI แดง
  • trigger ที่ opened, synchronize, reopened และ workflow_dispatch, ใช้ concurrency ยกเลิก run เก่า, continue-on-error, timeout-minutes: 20
  • ต้องมี actions/setup-node ไม่อย่างนั้น guard รันไม่ได้และจะ fail open
  • PR จาก fork อื่นไม่ได้รับ secret job จะข้ามแบบ exit 0

ตาของคุณ: เดโม, diff, merge ด้วยมือ

  1. อ่าน AI review จดบรรทัด verdict และทุกแถว not found
  2. ทำตามบรรทัด Demo บนเครื่องตัวเองโดยเปิดแอป
  3. เปิดทุกแถว not found แล้วตัดสินว่าเกณฑ์ยังไม่ถูกพิสูจน์จริง หรือ reviewer หาไม่เจอ
  4. อ่าน Merge danger เทียบกับ git log main..
  5. Merge ด้วยมือ: gh pr merge <n> --squash จาก terminal ของคุณเอง แล้วรัน frontier query จะเห็น ticket ที่ถูกปลดบล็อก

เมื่อรีวิวผิด แทบไม่ต้องแก้โค้ด ให้แก้ reviewer.md, แก้ ticket หรือเพิ่ม glob แคบๆ ใน allow list ห้ามใช้ --trust-all-tools

สรุปบทที่ 8

  • reviewer แบบ cold หาสิ่งที่ต่างออกไป แต่เดโมไม่ได้ บรรทัดสุดท้ายจึงเป็นคำแนะนำให้คนที่จะเดโม
  • อ่านอย่างเดียวด้วยสามชั้น: permission rules, guard hook และ brief
  • agent เขียนไฟล์เท่านั้น workflow โพสต์ด้วย --comment การ approve และ merge เป็นของคน
  • เป็นคำแนะนำใน workflow แยก ไม่ทำให้ PR fail และข้ามอย่างสะอาดเมื่อไม่มี key
ทำไมห้ามใส่ --trust-all-tools ใน workflow
ในโหมด headless ทุก ask ถือเป็น deny ซึ่งทำให้ agent อ่านอย่างเดียว ธงนี้เปลี่ยน ask ทั้งหมดเป็น allow คืนคำสั่งทุกตัวที่ deny list ไม่ได้ระบุให้ agent
ถ้ารีวิวขึ้นสถานะ approve จะต้องตรวจที่ไหนก่อน
agent โพสต์ไม่ได้ ดังนั้นบรรทัดโพสต์ใน ai-review.yml ถูกเปลี่ยน หรือมีคนโพสต์ด้วยธงผิด ให้ดู git log -p .github/workflows/ai-review.yml และใส่ --comment กลับ
